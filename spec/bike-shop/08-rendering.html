8. Rendering requirements

The visual design is free. These requirements set the limits every design shall respect. They are checked at two viewports: narrow 360 × 740 and wide 1280 × 800, in the light color scheme.

The checked states are:

State How it is reached
Load The page has loaded.
Full order Four lines with different bikes, each with at least two accessories and a quantity of at least 2, and a code applied. The height field then holds a height whose recommended frame is S, so that the configurator shows frame S with 29" wheels, Pro Electronic 2×12 and Glacier unavailable. The user then checks Rear rack (notice visible) and clicks add-to-order, which is refused (line-error visible).
Edit The full order, with its last line being edited.
Confirmation The full order placed.

A control is any <input> or <button> listed in 03-ui-contract, and any option card, that is visible in the state checked.

DR-LAY-01 No horizontal scrolling

  • Statement: In every checked state at both viewports, the system shall not make the page wider than the viewport: document.documentElement.scrollWidth shall not exceed window.innerWidth.
  • Rationale: A phone user never scrolls sideways to reach a price or a button.
  • Verification: Test
  • Acceptance criteria:
Scenario: Full order on a phone
  Given the viewport is 360 × 740
  When the user builds the full order
  Then the page is not wider than the viewport

DR-LAY-02 Reachable controls

  • Statement: In every checked state at both viewports, each control shall be reachable: at one at least of the three window scroll positions below, the center of the control's bounding box is inside the viewport and document.elementFromPoint at that center returns the control or one of its descendants (for an option card: the card or one of its descendants).

    1. The position reached by element.scrollIntoView({ block: "center" }) on the control.
    2. The top of the page (window.scrollTo(0, 0)).
    3. The bottom of the page (window.scrollTo(0, document.documentElement.scrollHeight)).

    For the input of an option card, the check is made on the card that contains it: its bounding box, scrollIntoView and elementFromPoint are taken on the card, which passes when elementFromPoint returns the card or one of its descendants.

  • Rationale: No control is covered by another element or kept out of the screen, whatever sticky or fixed parts the design uses.

  • Verification: Test

  • Acceptance criteria:

Scenario: Order buttons on a phone
  Given the viewport is 360 × 740
  When the user builds the full order
  Then place-order, promo-apply and every Remove button are reachable

DR-FOC-01 Visible keyboard focus

  • Statement: When a control receives the focus from the Tab key, the system shall make that focus visible: the control, or for the input of an option card the card itself, shall differ from its unfocused state in at least one of its computed outline-style, outline-width, outline-color, box-shadow, border-top-color or background-color. Within a radio group, the radio that receives the focus from the Tab key is the checked one, or the first one in DOM order when none is checked; arrow keys are not used to move the focus in this check.
  • Rationale: A keyboard user always sees where the focus is.
  • Verification: Test
  • Acceptance criteria:
Scenario: Focus on a frame card
  Given the user fills height-input with "170"
  And the radio "Frame M" is checked
  When the user moves the focus with Tab to the radio "Frame M"
  Then card-frame-M looks different from its unfocused state

DR-CON-01 Text contrast

  • Statement: For the text of each element below, in every checked state at both viewports, the contrast ratio between the computed color and the effective background shall be at least 4.5:1, computed with the WCAG 2.2 formula. The effective background of an element is obtained by blending, from the root down to the element, the computed background-color of each ancestor and of the element itself, starting from white. When the computed color has an alpha below 1, it is first blended over the effective background, and the ratio is computed between the resulting opaque color and the effective background. These elements, and their ancestors, shall not show their text over a background-image, and shall have a computed opacity of 1. Disabled <button> elements are exempt. Only the listed elements that are visible (README, section 2.5) in the checked state are checked. The [data-role="name"] and [data-role="price"] of every card are checked whether the option is available or not, and the [data-role="reason"] of every unavailable card is checked.
Elements
[data-role="name"], [data-role="price"] and [data-role="reason"] of every card
height-error, height-recommendation, add-hint, line-error, promo-error, promo-status, place-hint, notice
bike-price, qty-value, every [data-role] element of the order lines and summary lines
the text of every enabled <button> of 03-ui-contract
every data-testid element of the confirmation
  • Rationale: Every price, message and action stays readable.
  • Verification: Test
  • Acceptance criteria:
Scenario: Messages readable
  When the user fills height-input with "140"
  Then the contrast of height-error is at least 4.5:1

DR-ANI-01 Finite animations

  • Statement: The system may run animations with an infinite iteration count only on decorative elements that carry no data-testid, contain no control and contain none of the elements listed in DR-CON-01. Every other animation and transition shall finish within 1 second of the event that starts it.
  • Rationale: Values are read on a settled page; a page that never settles cannot be read.
  • Verification: Test
  • Acceptance criteria:
Scenario: Settled after a choice
  When the user selects card-frame-M
  Then within 1 second no finite animation or transition is running

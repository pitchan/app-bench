6. Functional requirements — Promo code, order amounts, delivery

6.1 Promo code

FR-PRM-01 Applying a code

  • Statement: While the content of promo-input is empty after removing leading and trailing whitespace, the system shall disable promo-apply. When the user activates promo-apply, or presses Enter in promo-input while promo-apply is enabled, the system shall compare the content with the catalog codes after removing leading and trailing whitespace and ignoring letter case. If it is a catalog code, the system shall make it the applied code, replacing any previous one, clear promo-input and hide promo-error. If it is not, the system shall show promo-error with MSG-20, keep the content of promo-input and keep the applied code, if any; promo-error shall be hidden at the next input event of promo-input.
  • Rationale: One code at a time, typed without worrying about case or stray spaces.
  • Verification: Test
  • Acceptance criteria:
Scenario: Code typed in lower case
  When the user applies " team15 "
  Then promo-status is visible
  And promo-input has the value ""

Scenario: Unknown code keeps the applied one
  When the user applies "FREESHIP"
  And the user applies "NOPE"
  Then promo-error reads "This code is not valid."
  And promo-input has the value "NOPE"
  And promo-status reads "FREESHIP applies once the order holds a bike."

FR-PRM-02 Code status

  • Statement: While a code is applied, the system shall show promo-remove and show in promo-status: for SPRING10 not active, MSG-22; for WELCOME50 not active, MSG-23; for FREESHIP not active, MSG-24; for TEAM15 not active, MSG-25; for TEAM15 active while the volume discount is used (02-catalog-and-rules, section 2.5, step 6), MSG-26; in every other case, MSG-21. The status shall follow every change of the order.
  • Rationale: The customer knows whether the code counts and, when it does not, why.
  • Verification: Test
  • Acceptance criteria:
Scenario: WELCOME50 stops with a second bike
  When the user applies "WELCOME50"
  And the user adds a bike "Frame M"
  Then promo-status reads "Code WELCOME50 applied."
  When the user adds a bike "Frame L"
  Then promo-status reads "WELCOME50 applies to an order of one bike only."

FR-PRM-03 Removing a code

  • Statement: When the user activates promo-remove, the system shall remove the applied code and hide promo-status and promo-remove.
  • Rationale: A code can be taken back.
  • Verification: Test
  • Acceptance criteria:
Scenario: Remove
  When the user applies "SPRING10"
  And the user clicks promo-remove
  Then promo-status is not visible
  And promo-remove is not visible

6.2 Order amounts

FR-AMT-01 Order amounts

  • Statement: The system shall compute every amount of the order with the steps, rounding and rules of 02-catalog-and-rules, section 2.5, for any order the user can build, with any applied code.
  • Rationale: The amounts are the contract with the customer.
  • Verification: Test, on orders and codes that are not given in this specification.
  • Acceptance criteria:
Scenario: One bike with the commuter pack
  When the user adds a bike "Frame M, Mudguards, Rear rack, Lights"
  Then summary-line-bikes has the value "€1,313.90"
  And summary-line-shipping has the value "€49.00"
  And summary-line-total has the value "€1,362.90"

FR-AMT-02 Order summary lines

  • Statement: While the order has at least one line, the system shall show the summary lines below, in the order of 03-ui-contract, with the given label in [data-role="label"] and value in [data-role="value"]; while it has none, no summary line shall be visible.
Key Label Value Shown while
bikes Bikes bikes amount (step 3), amount format always
pack Commuter pack sum of the commuter pack amounts (step 2), discount format that sum is greater than 0
volume Volume discount the volume discount used (step 6), discount format it is greater than 0
promo Promo {code} with the applied code in capitals promo discount (step 8), discount format it is greater than 0
shipping Shipping Free when shipping is 0, otherwise the shipping amount, amount format always
total Total total, amount format always
vat VAT included VAT included, amount format always
delivery Delivery delivery date (FR-DLV-01), date format always

The bikes value is the bikes amount, which already includes the commuter pack; the pack line shows how much of it comes from the pack.

  • Rationale: The customer sees each discount that applies, and only those.
  • Verification: Test
  • Acceptance criteria:
Scenario: Conditional lines
  When the user adds a bike "Frame M"
  Then summary-line-pack is not visible
  And summary-line-volume is not visible
  And summary-line-promo is not visible
  And summary-line-total is visible

FR-AMT-03 Live recalculation

  • Statement: When the order or the applied code changes, the system shall update the order lines, the summary lines, promo-status and place-order immediately, without any confirmation button. Changes of the configurator that do not change the order shall not change the summary.
  • Rationale: The order total reflects the order, not the bike being configured.
  • Verification: Test
  • Acceptance criteria:
Scenario: Configurator changes do not touch the order
  When the user adds a bike "Frame L"
  And the user selects card-drivetrain-pro
  Then summary-line-bikes has the value "€1,240.00"

6.3 Delivery

FR-DLV-01 Delivery date

  • Statement: The system shall show in summary-line-delivery the delivery date of 02-catalog-and-rules, section 2.6, computed from the lines of the order, today and the time of now, in date format.
  • Rationale: The customer knows when the whole order arrives.
  • Verification: Test, on dates, times and orders that are not given in this specification.
  • Acceptance criteria:
Scenario: One essential bike on a Friday morning
  Given now is 2026-12-18 10:00
  When the user adds a bike "Frame M"
  Then summary-line-delivery has the value "Tuesday, 29 December 2026"

"X has the value v" means that the [data-role="value"] element of summary line X reads v.

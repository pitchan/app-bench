7. Functional requirements — Quantity, promo code, price, summary, delivery

7.1 Quantity

FR-QTY-01 Quantity stepper

  • Statement: When the user activates qty-increase or qty-decrease, the system shall add or subtract 1 to the quantity and show it in qty-value.
  • Rationale: A customer may order the same bike for several riders.
  • Verification: Test
  • Acceptance criteria:
Scenario: Stepping
  When the page loads
  Then qty-value reads "1"
  When the user activates qty-increase twice
  Then qty-value reads "3"
  When the user activates qty-decrease
  Then qty-value reads "2"

FR-QTY-02 Quantity limits

  • Statement: While the quantity is 1, the system shall disable qty-decrease; while it is 5, the system shall disable qty-increase.
  • Rationale: The workshop builds 1 to 5 identical bikes per order.
  • Verification: Test
  • Acceptance criteria:
Scenario: Bounds
  When the page loads
  Then qty-decrease is disabled and qty-increase is enabled
  When the user activates qty-increase four times
  Then qty-value reads "5" and qty-increase is disabled

7.2 Promo code

FR-PRM-01 Promo field and Apply button

  • Statement: While the content of promo-input is empty after removing leading and trailing whitespace, the system shall disable promo-apply. When the user presses Enter in promo-input while promo-apply is enabled, the system shall act as promo-apply.
  • Rationale: An empty code cannot be applied by mistake.
  • Verification: Test
  • Acceptance criteria:
Scenario: Empty field
  When the user fills promo-input with "   "
  Then promo-apply is disabled

Scenario: Enter applies
  When the user types "FREESHIP" in promo-input and presses Enter
  Then promo-status shows "Code FREESHIP applied."

FR-PRM-02 Code normalization

  • Statement: When a code is applied, the system shall compare it with the catalog codes after removing leading and trailing whitespace, ignoring letter case.
  • Rationale: Customers type codes in any case.
  • Verification: Test
  • Acceptance criteria:
Scenario: Lower case with spaces
  Given the user selected card-frame-XL and card-drivetrain-pro
  When the user applies "  spring10 "
  Then promo-status shows "Code SPRING10 applied."
  And promo-input is empty
  And the value of summary-line-promo reads "−€198.00"

FR-PRM-03 Unknown code

  • Statement: If the code applied is not a catalog code, then the system shall show promo-error with MSG-10, keep the content of promo-input, and keep the previously applied code, if any, unchanged. promo-error shall be hidden on the first input event of promo-input after it is shown (without waiting for the field to lose focus), or when a code is applied.
  • Rationale: A typo never removes a valid code already applied.
  • Verification: Test
  • Acceptance criteria:
Scenario: Typo after a valid code
  Given FREESHIP is applied
  When the user applies "FREESHPI"
  Then promo-error shows "This code is not valid."
  And promo-input still contains "FREESHPI"
  And promo-status shows "Code FREESHIP applied."
  When the user types one more character in promo-input
  Then promo-error is not visible

FR-PRM-04 Applying a known code

  • Statement: When a catalog code is applied, the system shall make it the applied code, replacing any previous one, and clear promo-input.
  • Rationale: Codes do not stack; the last one wins.
  • Verification: Test
  • Acceptance criteria:
Scenario: Replacement
  Given WELCOME50 is applied
  When the user applies "FREESHIP"
  Then promo-status shows "Code FREESHIP applied."
  And promo-input is empty
  And summary-line-promo is not visible

FR-PRM-05 Applied code status

  • Statement: While a code is applied, the system shall show promo-remove and show promo-status with MSG-11 while the code is active, MSG-12 while SPRING10 is applied but not active, or MSG-13 while WELCOME50 is applied but not active. The status shall follow every configuration change without a new application of the code; a code that becomes active again applies its discount again. While no frame is selected, SPRING10 is not active. While no code is applied, promo-status and promo-remove shall not be visible.
  • Rationale: A code stays with the order; the customer sees when its condition stops or starts being met.
  • Verification: Test
  • Acceptance criteria:
Scenario: SPRING10 crosses its threshold
  Given the configuration of example P6 and SPRING10 applied
  Then promo-status shows "SPRING10 requires €1,500.00 or more after the quantity discount."
  When the user checks "Kickstand"
  Then promo-status shows "Code SPRING10 applied."
  And the value of summary-line-promo reads "−€150.45"
  When the user unchecks "Kickstand"
  Then summary-line-promo is not visible

Scenario: WELCOME50 and quantity 3
  Given WELCOME50 is applied and the quantity is 2
  When the user activates qty-increase
  Then promo-status shows "WELCOME50 cannot be combined with the quantity discount."

FR-PRM-06 Removing a code

  • Statement: When the user activates promo-remove, the system shall remove the applied code and hide promo-status and promo-remove.
  • Rationale: The customer can go back to the price without code.
  • Verification: Test
  • Acceptance criteria:
Scenario: Remove
  Given WELCOME50 is applied
  When the user activates promo-remove
  Then promo-status and promo-remove are not visible
  And summary-line-promo is not visible

7.3 Price

FR-PRC-01 Price calculation

  • Statement: The system shall compute every amount of the summary with the steps, rounding and rules of 02-catalog-and-rules, section 2.4, and shall produce the values of the worked examples P1 to P7 of section 2.7.
  • Rationale: The price shown is the price charged, to the cent.
  • Verification: Test
  • Acceptance criteria:
Scenario Outline: Worked examples
  Given the configuration of example <example>
  Then the summary values equal the row <example> of section 2.7

  Examples:
    | example |
    | P1      |
    | P2      |
    | P3      |
    | P4      |
    | P5      |
    | P6      |
    | P7      |

FR-PRC-02 Live recalculation

  • Statement: When any part of the configuration changes, the system shall update the summary, the bike preview and the delivery date immediately, without any confirmation button.
  • Rationale: The customer sees the effect of each choice as they make it.
  • Verification: Test
  • Acceptance criteria:
Scenario: Immediate update
  Given the user selected card-frame-M
  When the user checks "Lights"
  Then the value of summary-line-unit reads "€1,229.90" without any other action

FR-PRC-03 No frame selected

  • Statement: While no frame is selected, the system shall show in summary-line-frame the label Frame and the value — (U+2014 EM DASH), show — as the value of summary-line-unit, summary-line-subtotal, summary-line-shipping, summary-line-total and summary-line-vat, and hide summary-line-qty-discount and summary-line-promo.
  • Rationale: A bike without frame has no price.
  • Verification: Test
  • Acceptance criteria:
Scenario: Before any frame
  When the page loads
  Then the label of summary-line-frame reads "Frame" and its value reads "—"
  And the value of summary-line-total reads "—"
  And summary-line-delivery shows a date

7.4 Summary

FR-SUM-01 Summary lines

  • Statement: The system shall display the summary lines in the order of 03-ui-contract, section 3.2, with the texts below. While no frame is selected, FR-PRC-03 replaces the frame line and the amounts.
Key [data-role="label"] [data-role="value"]
frame Frame {size} frame price, amount format
wheels accessible name of the wheels surcharge, signed format
drivetrain accessible name of the drivetrain surcharge, signed format
color accessible name of the color surcharge, signed format (Included while waived)
accessory-<id> accessible name of the accessory price, signed format
unit Unit price amount format
quantity Quantity × {n} (U+00D7, one space, the quantity)
subtotal Subtotal amount format
qty-discount Quantity discount (5%) discount format
promo Code {code} discount format
shipping Shipping Free when zero, otherwise amount format
total Total amount format
vat Including VAT (20%) amount format
delivery Estimated delivery date format
  • Rationale: The customer can check every line of the price.
  • Verification: Test
  • Acceptance criteria:
Scenario: Example P1
  Given the configuration of example P1
  Then the summary lines read, in order:
    | label                   | value       |

    | Racing Red              | +€60.00     |
    | Mudguards               | +€45.00     |
    | Rear rack               | +€69.00     |
    | Unit price              | €1,774.00   |
    | Quantity                | × 3         |

    | Including VAT (20%)     | €758.39     |
    | Estimated delivery      | (date)      |

FR-SUM-02 Conditional summary lines

  • Statement: The system shall show summary-line-accessory-<id> only for selected accessories, summary-line-qty-discount only while the quantity is 3 or more and a frame is selected, and summary-line-promo only while a frame is selected and the applied code is active with a promo discount greater than zero. FREESHIP therefore never shows a promo line.
  • Rationale: The summary lists what applies, nothing else.
  • Verification: Test
  • Acceptance criteria:
Scenario: FREESHIP
  Given the user selected card-frame-M and applied FREESHIP
  Then summary-line-promo is not visible
  And the value of summary-line-shipping reads "Free"

FR-SUM-03 Summary value formats

  • Statement: The system shall format every summary value with the formats of 02-catalog-and-rules, section 2.6.
  • Rationale: One reading format for every price.
  • Verification: Test
  • Acceptance criteria:
Scenario: Minus sign
  Given the configuration of example P3
  Then the value of summary-line-promo is "−€50.00" written with U+2212

7.5 Delivery

FR-DLV-01 Lead time

  • Statement: The system shall compute the lead time with 02-catalog-and-rules, section 2.5, step 1. The lead time is not displayed; it is verified through the delivery date of FR-DLV-02.
  • Rationale: Build time depends on parts, paint and volume.
  • Verification: Test
  • Acceptance criteria:
Scenario: Example D2 (lead time 17)
  Given today is 2026-12-18
  When the user selects card-drivetrain-pro and card-color-red and activates qty-increase twice
  Then the value of summary-line-delivery reads "Monday, 18 January 2027"

FR-DLV-02 Delivery date

  • Statement: The system shall show in summary-line-delivery the delivery date of 02-catalog-and-rules, section 2.5, step 2, in date format, whether a frame is selected or not, and shall produce the worked examples D1 to D3.
  • Rationale: The customer knows when the bike arrives before ordering.
  • Verification: Test
  • Acceptance criteria:
Scenario: Closed days are skipped
  Given today is 2026-12-18
  When the page loads
  Then the value of summary-line-delivery reads "Tuesday, 29 December 2026"

Scenario: Counting starts after a Saturday
  Given today is 2026-11-14
  When the user selects card-drivetrain-sport and card-color-sand
  Then the value of summary-line-delivery reads "Tuesday, 24 November 2026"

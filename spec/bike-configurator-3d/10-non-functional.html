10. Non-functional requirements

NFR-PKG-01 Single file delivery

  • Statement: The system shall be delivered as one file named index.html, starting with <!DOCTYPE html>, containing all of its HTML, CSS, JavaScript and SVG inline.
  • Rationale: The page opens directly from the file system with no installation.
  • Verification: Test
  • Acceptance criteria:
Scenario: Opened from disk
  When index.html is opened through a file:// URL
  Then the configurator is usable
  And no error is reported in the browser console

NFR-NET-01 No network access

  • Statement: The system shall not issue any network request (scripts, stylesheets, fonts, images, data) other than loading index.html itself.
  • Rationale: The page works offline and loads instantly.
  • Verification: Test
  • Acceptance criteria:
Scenario: No request
  When the page loads and the user configures and orders a bike
  Then no request other than the page itself was made

NFR-DLG-01 No native dialogs

  • Statement: The system shall not call window.alert, window.confirm or window.prompt.
  • Rationale: Every message has its place in the UI contract.
  • Verification: Test
  • Acceptance criteria:
Scenario: No dialog in any flow
  When the user performs every flow of this specification
  Then no native dialog is opened

NFR-A11Y-01 Native controls and accessible names

  • Statement: The system shall use native <input> and <button> elements for every control of 03-ui-contract, with the accessible names given there, so that each control can be found by its role and exact accessible name.
  • Rationale: Controls work with assistive technologies and the keyboard.
  • Verification: Test
  • Acceptance criteria:
Scenario: Roles and names
  When the page loads
  Then there is exactly one radio named "Frame M"
  And there is exactly one checkbox named "Rear rack"
  And there is exactly one textbox named "Your height (cm)"
  And there is exactly one button named "Increase quantity"

NFR-A11Y-02 Live announcements

  • Statement: The system shall place notice inside a distinct element with role="status" that is in the DOM from page load and never hidden with display: none, visibility: hidden or the hidden attribute, and shall write cascade messages into that element. While height-error or promo-error is visible, the system shall set aria-invalid="true" on its field and reference the error element from the field's aria-describedby; while the error is not visible, aria-invalid shall be absent or "false".
  • Rationale: Screen readers announce automatic changes and which field is wrong.
  • Verification: Test
  • Acceptance criteria:
Scenario: Live region present at load
  When the page loads
  Then an element with role "status" exists and does not have display "none"
  And notice is not visible

Scenario: Height error association
  When the user fills height-input with "140"
  Then height-input has aria-invalid "true"
  And the aria-describedby of height-input contains the id of height-error
  When the user fills height-input with "170"
  Then height-input has no aria-invalid "true"
